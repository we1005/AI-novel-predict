# 03 · 预测链路

> 给定"已写到第 N 章"，**发散 → 收敛 → 执行**三段式产出剧情走向。两个尺度：单章/小段（`/predict`）与全弧 100+ 章（`/predict/arc`）。

> **🔄 实现现状（2026-06 更新）**——本文档原始版基于早期实现，以下是与当前代码的关键差异：
> 1. **多服务商**：模型走阿里 DashScope + 火山引擎 Coding-Plan，按 agent 路由。
> 2. **结构化输出全部改 JSON-in-text，不再用 forced tool_choice**：doubao 系推理模型在大上下文（预测上下文约 9 万字）下强制工具调用会**静默吞输出**（`finish=tool_calls` 但工具数组空、正文空），实测 predict/arc 整条死掉。现统一：系统提示里贴严格 JSON schema、不带 `tools`、`json_repair` 解析正文。
> 3. **模型路由**：结构化候选/评分（diverge/score）→ `doubao-seed-2.0-code`（JSON 干净）；散文执行（writer）→ `minimax-m3`（文笔最佳）。
> 4. **winner 兜底**：`_ensure_winner` / `_ensure_arc_winner`——评分偶发 `winner_index=null` 时取综合分最高者，防止 outline 崩溃。
> 5. 之上新增**整本故事弧推演**（[07](./07-整本故事弧推演链路.md)）：把 arc 骨架逐阶段展开成整本书逐章大纲。

## 1 · 为什么是三段而非一段？

让 LLM 一次性"基于上下文给出一个合理续写"是常见错法——它会：

1. 选**最安全**的方向（最像已写的章节），失去戏剧张力
2. 把多个候选混在一段里，输出无法被评估
3. 一次提交后无法重选

我们让模型先**分头想**（高 T 发散）、再**统一打分**（低 T 收敛）、最后**忠实执行**选中方向（中 T 流式输出）。

```
      Stage A                    Stage B                Stage C
┌──────────────────┐      ┌────────────────┐      ┌──────────────┐
│  Diverger        │      │ Scorer         │      │ Writer       │
│  T=0.95, top_p   │      │ T=0.2          │      │ T=0.75       │
│  =0.95           │  →   │ tool_use       │  →   │ stream_text  │
│  生成 N 条候选    │      │ 返回 winner    │      │ 落 1-3 章    │
│  uses_foreshadow │      │ + 评分理由     │      │ 风格参考注入  │
└──────────────────┘      └────────────────┘      └──────────────┘
```

## 2 · Stage A：发散（diverger）

文件：`backend/app/predict/pipeline.py::stage_a`

```python
# 当前实现：JSON-in-text（贴 schema，无 tools），doubao-code 解析干净。
resp = llm.call(
    agent="predict.diverge",
    model=MODEL_STRONG,                              # 经路由 → doubao-seed-2.0-code
    system=[CANDIDATE_SYSTEM + CANDIDATE_JSON_HINT, *_ctx_blocks(ctx)],
    messages=[{"role": "user", "content": user}],
    temperature=0.95, top_p=0.95, max_tokens=8000,
)
cands = _loads_json(resp.text).get("candidates", [])   # json_repair 兜底
```

输出 schema 要点：

```jsonc
{
  "candidates": [
    {
      "title": "...",
      "synopsis": "≤300 字概要",
      "key_beats": ["..."],
      "uses_foreshadow_ids": [3, 17, 42],   // 必须引用真实 ID
      "tone": "悬疑 / 战斗 / 文戏",
      "risks": ["..."]
    }, ...
  ]
}
```

**约束**：候选必须**走向迥异**（system prompt 强调），并且 `uses_foreshadow_ids` 引用真实存在的伏笔 ID（防止幻觉）。

注入的上下文：未收束伏笔 + 世界规则 + 主角状态 + 近期 PlotPoint + Mystery + 最近 5 章标题。

## 3 · Stage B：收敛（scorer）

```python
SCORING_TOOL = {
  "scores": [
    {"index": 0, "scores": {"foreshadow": 8, "character": 7, "style": 9, "novelty": 6, "world": 9}, "rationale": "..."},
    ...
  ],
  "winner_index": 2,
  "winner_rationale": "..."
}
```

`temperature=0.2` 让评分稳定。注意 Stage A 同 ctx 的 cached_block 在 B 完全复用——只多发一次评分指令的 user prompt。

## 4 · Stage C：执行（writer，流式）

文件：`pipeline.py::stage_c_stream`

```python
# 风格参考：用 winner 的 synopsis 当 query 走 FTS 召回最近几章原文片段
style_hits = fts_recall.search(synopsis, limit=4, before_chapter=after+1)
blocks = [*_ctx_blocks(ctx), cached_block("【风格参考片段】\n" + style_hits)]

for chunk in llm.stream_text(model=MODEL_STRONG, T=0.75, max_tokens=8000):
    yield chunk
```

**关键**：FTS 召回的片段不是给"剧情灵感"，是给**笔法范本**——避免模型滑成 GPT-4 风格的中文，要锁住作者本人的腔调。

`stream_text` 走 SSE 直传到前端，用户立即看到字。

## 5 · 全弧版：`/predict/arc`

文件：`backend/app/predict/arc.py`

跟单章版一样三段，但目标变成 **100-200 章宏观弧**：

| 阶段 | 单章版 | 全弧版 |
|---|---|---|
| 发散 | 5 个 1-3 章候选 | 3 个 100-200 章主线候选 |
| 收敛 | 同上 schema | 评估"是否能塞进所有 open mysteries" |
| 执行 | 流式落正文 | 输出 phase 列表（每 phase 描述 10-30 章干什么） |

输出 schema 比单章版重——每个 arc 含 `phases[]`，每个 phase 有 `chapter_range` / `summary` / `must_include_foreshadow_ids` / `key_events`。这个 schema 是后续 `/outline/refine` 的输入源。

`/predict/arc/run` 调用约 90-120 秒 / ~$0.05-0.10。

## 6 · 数据落库

| 表 | 字段 |
|---|---|
| `PredictionRun` | after_chapter, candidates_json (A), scores_json (B), chosen_index, written_text (C), cost_usd |
| `ArcRun` | after_chapter, n_candidates, target_chapters, candidates_json, scores_json, user_hints |

每次跑都新增一条，可在 `/predict` / `/arc` 页面回看历史。

## 7 · 与其他链路的衔接

```
arc 或 predict 选定 winner
       │
       ▼
/outline/refine?source_kind=arc&source_run_id=...&chosen_index=...
       │
       ├─▶ 单 phase：OutlineRun (细化该 phase 内的章节大纲)
       │
       └─▶ 整本：/predict/arc/runs/{id}/project  → 逐 phase 展开+章号重锚+完整性裁决
       │                                          （见 07-整本故事弧推演链路）
       ▼
/draft/write (Writer + 3 Reviewers + Editor + 确定性门控)
       │
       ▼
ChapterDraft.final_text  → 入 corpus，下一轮 ingest
```

## 8 · 模型温度速查

| 阶段 | T | top_p | 理由 |
|---|---|---|---|
| Stage A 发散 | 0.95 | 0.95 | 候选必须迥异，多样性优先 |
| Stage B 收敛 | 0.2 | — | 评分必须稳定 |
| Stage C 执行 | 0.75 | — | 既要灵气又不能跑偏 |
| arc Stage A | 0.9 | — | 100 章规模，过散就不一致 |
