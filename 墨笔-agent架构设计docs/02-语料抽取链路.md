# 02 · 语料抽取链路

> 把 1472 章原文嚼成可被 agent 调用的结构化记忆。**一次性完成 + 增量补足**——新写出的章节会再次进入这条链路。

> **🔄 实现现状（2026-06 更新）**：
> 1. **抽取 JSON-in-text 兜底**：6 个抽取 agent 共用的 `_agent_call` 先走 forced tool_choice（小书首试即过），若返回空 tool_use / 客户端空守卫抛错（大书后期批次实体表上下文可能破 9 万字、doubao 系吞输出）→ **自动回退 JSON-in-text**（贴 schema + `json_repair`）。
> 2. **多服务商**：抽取 agent 混合路由（entity/foreshadow → qwen3.5-flash，state 等 → doubao-seed-2.0-lite）。
> 3. **图谱去重健壮性**：`_alias_strs` 兼容任意形状的 `aliases_json`（抽取模型偶尔把元数据 dict 塞进别名字段 → 旧去重直接崩 500）。
> 4. **进度/健壮性**：进度条改**覆盖率**驱动（已抽章节÷总章节，钳 100%）；批次异常路径加 `if b:` 守卫，避免卡在 "running" 导致 `run_all` 死锁。
> 5. **实体去重 / 关系抽取 / 重要度重算 / 多视角**：见图谱模块——LLM 判定合并同实体（FK 全量重指向）、关系边、重要度、宝物目录兜底。

## 1 · 整体流程

```
小说.txt
   │
   ▼
[ 0 ] 分章 split.py
   ├─ 正则识别 "第 N 章 标题"
   ├─ 不切原文，记录 char_offset_start/end
   └─ 写入 Chapter 表
   │
   ▼
[ 1 ] 批划分 (5-20 章/批，可调)
   │
   ▼
[ 2 ] 每批顺序跑 6 个 agent (extract.py::run_batch)
   ├─ entity     → Entity 表
   ├─ foreshadow → Foreshadowing 表
   ├─ state      → EntityState 表
   ├─ plot       → PlotPoint 表
   ├─ world      → WorldRule 表
   └─ mystery    → Mystery 表 (跨批维护)
   │
   ▼
ExtractionBatch.status = done
LLMCall × 6 写入审计表
```

入口端点：`POST /ingest/extract?start=1&end=21` → 后台异步调度。
全书重跑：`backend/app/ingest/extract.py::run_all()`，可并行多批。

## 2 · 6 个抽取 Agent

每个 agent 都是「**强制 JSON 工具调用**」——`tool_choice` 锁定到唯一工具，模型必须填 schema 字段，避免 Markdown / 自然语言污染。

| Agent | 职责 | Schema 主字段 | 模型 / 温度 |
|---|---|---|---|
| **entity** | 抽新登场的命名实体 | `entities[].{type, name, aliases, description}` | FAST / 0.3 |
| **foreshadow** | 标 planted / resolved 伏笔 | `planted[]`, `resolved[]` | FAST / 0.3 |
| **state** | 关键人物状态变化 | `states[].{character, state_after, diff, note}` | FAST / 0.3 |
| **plot** | 重要剧情节点 | `plot_points[].{summary, importance}` | FAST / 0.3 |
| **world** | 世界设定术语 | `rules[].{term, definition}` | FAST / 0.3 |
| **mystery** | 读者未解的悬念（增量） | `actions[].{op: add/sharpen/resolve, ...}` | FAST / 0.3 |

> Prompt 与 schema 全部在 `backend/app/llm/prompts/extraction.py` + `mystery_per_batch.py`。

## 3 · 顺序与依赖

agent 必须**顺序跑**，不能并行：

```
entity → foreshadow → state → plot → world → mystery
```

理由：每个后续 agent 都需要看见前一个 agent 已写入的行。比如 `state` 要引用 `entity` 刚写入的人物 ID；`mystery` 要看到所有前 5 个 agent 的产物（实体/伏笔/状态/节点/规则）才能合理标注 clue。

实现细节（见 `extract.py::run_batch` line 520-545）：

```python
for name in ["entity", "foreshadow", "state", "plot", "world", "mystery"]:
    # 每个 agent 前重新 query 一次缓存上下文 —— 上一个 agent 写入的内容必须可见
    with session_scope() as s:
        _, sys_blocks = _build_cached_context(s)

    out, cost = _agent_call(name=name, ..., tool=agents[name]["tool"])
    # 在新 session 里 commit — 避免 audit insert 与外层事务死锁
    with session_scope() as s:
        _persist_for(name, s, out)
```

## 4 · Cached Prefix 优化

每批 6 个 agent 共享一组 `cached_block`：

```python
blocks = [
    cached_block("现有实体表 (JSON, 按 type/name 排序): " + json),
    cached_block("现有未收束伏笔表: " + json),
    cached_block("现有世界规则表: " + json),
    cached_block("需要 StateAgent 跟踪的核心人物名: " + json),
    cached_block("现有 mysteries 表: " + json),
]
```

第一个 agent 全付 input token；后 5 个走 `cache_read`，省 50-80% 输入成本。

**关键技巧**：`stable_json()` 保证序列化稳定（按字典序），cache key 才能命中。

## 5 · MysteryAgent：跨批增量

普通 agent 是**无状态**的——只看本批章节。但 mystery 必须**跨批累积**（一个悬念可能从第 100 章铺到第 1000 章才解开）。

设计：mystery agent 的输出不是"实体列表"，而是"动作列表"：

```jsonc
{
  "actions": [
    {"op": "add",     "question": "...", "category": "...", "severity": "...", "clue": "..."},
    {"op": "sharpen", "id": 17, "new_clue": "...", "confidence_delta": +10},
    {"op": "resolve", "id": 9, "explanation": "..."}
  ]
}
```

每批运行后追加到 `Mystery.updates_log_json`，按 `confidence` / `severity` 排序展示。

## 6 · 失败处理

每个 agent 调用都有：

- `try / except json.JSONDecodeError` → 触发 `json-repair` 兜底
- 任何 agent 失败 → `ExtractionBatch.status = "failed"` 但**不回滚已成功的前置 agent**（因为部分抽取也是有价值的）
- `LLMCall` 表始终入库，便于事后查 cost/失败率

## 7 · 全书规模 / 成本

实测 1472 章：

| 指标 | 值 |
|---|---|
| 批数（10 章/批） | 148 |
| 总 LLM 调用 | ~890 (6 × 148 + 偶发重试) |
| 输入 tokens | ~14M (含 cache hits) |
| 输出 tokens | ~2M |
| 总成本 | ~$5-8 (qwen3.5-flash) |
| 总耗时 | ~40-60 分钟 (并行 4 批) |

## 8 · 增量更新

新写出的章节通过 `/ingest/extract?start=N&end=N+1` 单批跑一次即可——cached prefix 自动加载已有的全部累积上下文。

## 近期更新（2026-06）

**1. 批次粒度修复（漏抽 bug）。** `run_all` 默认 50 章/批 + 抽取输出 4096 token，单次调用塞 50 章会严重漏抽（实测整本只得 125 实体/13 伏笔）。改 **4 章/批 + max_tokens 8000** 后恢复正常密度（304 实体/137 伏笔/225 情节/118 世界规则/168 状态）。

**2. 续写章回灌的章号归属修复。** `extract_one_chapter` 抽取续写章(157+)时，实体/伏笔的 `first_appear/planted_chapter` 字段有 FK→`chapters.number`，而续写章未登记进 chapters 表，导致章号被截到 corpus 末章(156)、错标成原著、无法按章清理。修复：回灌前先把续写章登记进 `chapters` 表，章号上限放宽到本批最大章。

**3. 抽取增量落盘（版本控制）。** `extract_one_chapter` 抽取时同时把 6-agent 原始输出写成 `repo/memory/increments/ch<N>.json`，作为「按章撤回/物化」的最小单元（详见 08-版本控制与可重建记忆）。
