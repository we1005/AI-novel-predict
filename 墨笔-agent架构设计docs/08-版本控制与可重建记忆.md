# 版本控制与可重建记忆（Git 管「源」· SQLite 当缓存）

> 目标：让正文、大纲、抽取记忆都**可回退、可重建、可分支**。撤回某章续写时，它的记忆贡献能一起干净退掉——而不是像早期那样污染整个记忆池、只能清库重来。

---

## 一、为什么需要它

早期记忆全压在 SQLite 里，而 SQLite 是关系型、带外键、原地修改——**天生难回退**。一次失败的通宵续写把约 200 个续写实体/伏笔混进了 corpus 记忆池，且因为没有按章归属，**无法外科式摘除，只能清库重抽**。这暴露了根本问题：记忆需要一个「源」，DB 只该是它的投影。

**裁决：Git 管「源」，SQLite 当可由「源」确定性重建的缓存。**

```
记忆 = baseline(corpus 1-156, 不可变)  ⊕  按章号顺序重放各章 increment
```

只要满足这个等式，「撤回第 N 章」= 删它那份 increment 文件 + 重新物化；importance 等累加量在重放时自然重建，删掉某章其贡献即消失。

---

## 二、每本书一个独立 git 仓

`backend/data/books/<slug>/repo/`，三棵树：

```
manuscript/   ch157.zh.md  ch157.en.md ...     ← 正文(中文定稿 / 双语英文)
outline/      （大纲/弧，规划层）
memory/
  baseline/   entities.json foreshadow.json …  ← 原著 1-156 抽取（不可变基线）
  increments/ ch157.json  ch158.json …          ← 每章抽取增量（6-agent 原始输出，可单独删/改）
```

- **独立仓、不嵌入项目仓**：`backend/data/` 已被项目 `.gitignore` 整目录忽略，故书稿仓的 `.git` 对项目全局 git **完全不可见**——无冲突、无 "embedded repository" 警告。不用 submodule（会把私密、巨大、高频变动的书稿与代码发布耦合，且 detached HEAD 等坑多）。每本书可推到**自己的 GitHub remote**。
- **`novel.db` 不入仓**：它是派生缓存，由 git 内容物化重建。书稿仓 `.gitignore` 排除所有 `*.db*`，保持纯文本、diff 友好。

---

## 三、三个关键设计点（让它真正可回退）

1. **增量按章独立成文件**。`memory/increments/ch157.json` 只装第 157 章 6 个抽取 agent 的原始结构化输出（新实体/伏笔/状态/世界规则/疑点动作）。撤回=删它；重写=覆盖它。
2. **聚合量「派生」而非「累加」**。物化时按章号顺序重放各章增量，importance 等累加量靠重放重建——删掉某章增量，其贡献自然消失，无需记 delta。
3. **物化确定性、幂等**。`materialize()`：清空记忆表 → 载入 baseline → 按章号顺序套用所有 increment（复用线上同一套 `_persist_dispatch`）→ 重建。同样的 git 状态永远物化出同样的 DB。**DB 坏了/脏了，删库重物化即可。**

## 五、能得到的操作

- **撤回第 N 章**：`revert_chapter(N)` —— 删 `manuscript/chN.*` + `increments/chN.json` → 重物化。记忆与正文一起干净回退。
- **改写第 N 章**：覆盖那几个文件 → commit → 物化，旧贡献自动不复存在。
- **剧情换走向**：`create_branch("what-if-185")` —— 在分支上重写 185 之后的章节，多结局并行探索，随时切回。
- **审计/对比**：`history("manuscript/ch200.zh.md")` 看一章演化；`git diff` 看两版差异。
- **协作/备份**：整本书（正文+记忆）就是个 git 仓，可 push、回滚到任意 commit。

## 六、第 0 步：建立干净 baseline（已落地）

1. 清空受污染的派生记忆（原生 sqlite3 + `PRAGMA foreign_keys=OFF` 一次清净）+ 删续写章登记/FTS，保留 corpus 1-156 原文。
2. 重抽 corpus 1-156。**踩坑**：原 `run_all` 用 50 章/批 + 抽取输出 4096 token，严重漏抽（只得 125 实体/13 伏笔）；改 **4 章/批 + 8000 token** 后恢复到实体 304/伏笔 137/情节 225/世界规则 118/状态 168。
3. `dump_baseline()` → `git commit` 首个 baseline。
4. `materialize()` 往返自测：清库 → 纯靠 git 重建 → 7 表计数与重建前完全一致（**PASS**）——验证「SQLite 是可重建缓存」成立。

## 七、润色建议（局部采纳 · 锚点失效检测）

把旧的「A·完整互译精修(全量重写中英)」重构为 **git-merge 式的局部建议**：不静默改原文，只产出"哪里该改成什么"的就地替换建议，用户逐条采纳。

- **产出**：`suggest_edits(draft_id)` 扫描中文定稿(吃 pitfalls + 世界观语域卡)→ 一组定位到**精确子串**的替换建议 `{quote, replacement, category(套路词/翻译腔/时代错置/文化语域), reason}`。
- **落库 + 版本控制**：建议存 `edit_suggestions` 表(刷新后仍在、可审计);同时 dump `repo/suggestions/ch<N>.json` 随 commit 进 git(建议过什么 vs 采纳了哪些，全可追溯)。第四棵树：
  ```
  suggestions/  ch157.json  ch173.json …   ← 每章建议(含锚点状态)
  ```
- **存取**：打开章节 = `GET /draft/suggestions` **读库**(免费、实时重算锚点)；点「🔄重新生成」= `POST /draft/suggest-edits` 跑 LLM 出新批(旧未应用标 superseded)。
- **锚点失效检测(核心)**：每条建议记 `base_hash`(生成时定稿哈希)。展示/应用时若 `quote` 在**当前**正文里找不到(原文被改过 / 被前一条采纳覆盖)→ 标 `stale`、置灰、禁止采纳，UI 显「⚠ 锚点失效(原文已改)」；`apply_edits` 应用时**再校验一次**，失效的计入 `failed` 返回，绝不错位乱改。
- **应用**：`apply_edits(draft_id, accepted_ids)` 按 id 就地替换中文定稿(只替第一次出现)→ 落库 → 导出 manuscript → git commit `ch<N>: 采纳 N 处润色建议`。采纳改了中文后，B 锚定的英文版标记过时(`en_stale`)，提示重生成。
- 文件：`backend/app/draft/suggest.py` · 端点 `/draft/suggest-edits` `/draft/suggestions` `/draft/apply-edits` · 前端 diff 面板在 `/draft` 章节详情。
