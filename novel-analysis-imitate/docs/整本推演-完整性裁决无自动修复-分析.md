## 结论:**单趟生成,没有针对该完整性裁决的自动打回修复。`needs_work` 是一次性诊断/警告。**

`project_full_book`(`backend/app/arc/project.py:176-255`)是**一趟到底**(源码注释即写 "Single-shot arc generation"):

```
_sanitize_phases(阶段章号结构)                      # 仅修单调/补缺口/够到结局,不碰内容
  → 逐阶段 outline.refine → 落 per-phase OutlineRun   # 展开
  → 汇总 all_chapters
  → _judge_completeness(arc, all_chapters) → verdict  # 完整性裁决
  → 存 verdict 并 return                               # 结束
```

裁决完**直接存 verdict 返回**,**没有 `while`/retry/repair 回路**。所以 `needs_work` + 未交代真相 + 未收束伏笔 id 都只是**输出给人看的诊断**,系统不会据此自动补大纲、也不会强制收束那批伏笔。这版大纲带着这些 gap 就是当前产物。

- 唯一的自动"修复"是 `_sanitize_phases`(`project.py:69`),只修**阶段章号结构**(garbled end<start、缺口、够到结局),**与内容完整性无关**。

## 有 repair,但在另一层、另一时机 —— 修不了这个

`bookwriter.repair_phase`(`backend/app/arc/bookwriter.py:128`)确实存在:"诊断→补大纲指令→重写相关章→回灌→复审"。但:
- 触发在**写作阶段**(`write_book` 逐阶段写完后),针对**写出来的成稿**——没成稿就 `skip`(`bookwriter.py:86`);
- 比对的是 `review_phase` 的 `foreshadow_missed`,即"该阶段**计划里有**、但成稿**漏掉**的伏笔",据此重写相关章;
- 逐阶段 + **人审 gate**。

**关键区别**:它只兜"大纲已安排、成稿没落实"的部分。而推演裁决里的 `still_open_foreshadow_ids`(10,12,…)是**整份大纲压根没安排到结局前收束**的伏笔——大纲没排,写作期 `repair_phase` 也不会凭空去收。因此这些 gap 会一路传到成稿。

## 实际含义 + 可选处理(仅说明)

`needs_work` 是**真实质量信号**:照这版大纲写,约 18 条伏笔不会收、部分核心真相(如天玉界崩塌完整原因)讲不透。系统不自动补。要收窄:

1. **手动编辑逐阶段大纲**(`/outline` 或 draft 页,已支持逐章改):把"收束 #10/#12…""点明紫菀血液异香含义"排进对应阶段的 `must_include`。
2. **重推一次**(`推演整本书`):但它**不吃回 verdict**、非确定性,可能改善也可能一样。
3. **换 / 重生成候选弧**:若 arc 本身就没规划这些收束(根因在 arc 层),换更完整的候选弧或重跑 arc 预测。
4. 写作期 `repair_phase` 能兜住"大纲已排、成稿漏掉"的那部分,兜不住大纲从没排的。

## 架构缺口 + 建议增强(未实施)

目前**没有**"`needs_work` → 把未交代真相 / 未收束伏笔作为强约束,自动重推一版大纲"的闭环——verdict 只输出、不回灌进 re-projection。

**建议(裁决驱动的定向重推)**:让 `_judge_completeness` 的 `unresolved_truths` / `still_open_foreshadow_ids` / `coherence_issues` 回灌进一次自动重推:把它们注入各阶段 `refine` 的 `must_include` / 续写约束("必须在结局前落实以下真相、收束以下伏笔 id"),重推后再裁决;可设 1–2 轮上限,仍 `needs_work` 则交人审。这样 `needs_work` 从"只报警"升级为"先自愈一轮再报警"。
